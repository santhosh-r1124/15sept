# 0003 — Schema ownership and migrations

- Status: Accepted
- Date: 2026-09-10
- Deciders: Platform team

## Context

Both the Python API and TypeScript packages need to know the database shape.
We must pick a single source of truth for table definitions and a migration
tool, avoiding two systems fighting over DDL.

## Decision

- **`apps/api` owns the schema**: SQLAlchemy 2.0 ORM models are the source of
  truth; **Alembic** generates and applies migrations
  (`apps/api/migrations/`).
- Alembic reads the app's own `Settings` (`DATABASE_URL_SYNC`, psycopg driver)
  and diffs against `Base.metadata`, so migrations always match app config.
- **`packages/database`** (TypeScript) is a *consumer*: a thin pooled client
  plus a generated `types.ts` regenerated from the migrated database. It defines
  nothing.
- Constraint/index naming uses a fixed convention (`app/db/base.py`) so
  autogenerated migrations are stable and reviewable.

## Consequences

- One command applies schema changes everywhere: `alembic upgrade head`.
- TS types can drift until regenerated; regeneration is a documented step
  (`packages/database/README.md`) and should run in CI once tables exist.
- Node code that needs data should prefer calling the API; direct DB access from
  `packages/database` is for scripts/seeders/edge cases.
- Every new model module must be imported in `app/models/__init__.py` or
  autogenerate misses it (`migrations/env.py` imports that package).

## Alternatives considered

- **Prisma (TS) owns schema** — better TS DX, but the API and every `services/*`
  are Python; reflecting Prisma-managed tables from Python is awkward and the
  Python side is where most data logic lives.
- **Raw SQL migrations** — maximum control, but we lose autogenerate and hand-
  write all DDL + types.
- **Supabase migrations / dashboard as source of truth** — couples schema
  history to one vendor and splits it from app code review.
